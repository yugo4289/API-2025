## 1. 背景・業務領域の具体化
- 対象ドメイン：日常生活・気象情報
- 現状業務（要約 5〜7行）：毎朝、スマートフォンで天気予報アプリを能動的に開き、情報を確認している。しかし、朝の多忙な時間帯において、雨が降るか晴れるかの判断や、予定に合わせた詳細な気象チェックは後回しになりがちである。また、複数のアプリを跨いで情報を収集するため、意思決定に時間がかかっている。これらを自動化し、本人の位置情報における天気の情報をプッシュ型で受け取れる仕組みがあれば日々の暮らしが便利になると考える。

- 課題の所在（箇条書き）：
朝の忙しい時間に確認を忘れ、出先で雨に降られる

天気が変わるリスクを考慮せず、予定を立ててしまう

複数の拠点の予報（自宅と職場など）を把握するのが面倒

- 制約条件（法規／組織／リソース／期間）：OpenWeatherMap無料枠のレート制限（60回/分）、LINE Messaging APIの無料メッセージ枠（200通/月）、個人情報の保護

---

## 2. 課題・目的・APIが必要な理由
- 解決すべき業務課題：毎朝の確認コストの削減と、週初めの準備の最適化
- APIの目的・役割：当日の予報を定期取得・解析し、ユーザーの設定条件に合致した際、LINEを通じて最適な行動指針（傘の要否など）を通知する
- 成功指標（KPI）：朝の天気確認時間の80%削減、通知成功率99.9%以上
  - 例：平均レスポンス < 300ms、エラー率 < 0.1%、作業時間 30%削減

## 6. 提案技術の比較（選定理由）

| 観点                      | 候補A | 候補B | 比較結論 |
| ----------------------- | --- | --- | ---- |
| APIスタイル（REST/GraphQL 等） | REST | GraphQL | REST: 学習コストが低く、シンプルなリソース操作に適している |
| データストア（RDB/NoSQL）       | MySQL | NoSQL | MySQL: ユーザーと設定情報の整合性を重視するため |
| 認証・認可（OAuth2/OIDC 等）    | OAuth2 | API Key | OAuth2: LINE連携時のIDトークン検証など安全性を確保 |
| デプロイ（クラウド/オンプレ）         | AWS | オンプレミス | クラウド: 外部API（LINE等）との接続性が良いため |

*   選定理由（トレードオフと採用根拠を3点以上）：FastAPI: Pydanticによる型定義が容易で、外部APIとの非同期通信による高速なレスポンスが可能。

LINE Messaging API: ターゲット層である学生・社会人が日常的に利用しており、プッシュ通知の到達率が極めて高い。

MySQL: ACID特性を活かし、通知設定（地域名や閾値）の不整合を防止する。

## 9. まとめ

*   要件の妥当性（根拠）：本APIは、日常的に発生する「気象確認」という受動的な業務を、APIによる「通知」に置き換えることで、生活や業務の質を向上させる。また日本で普及率の高いLINEをインターフェースに採用している点で、高い実用性と付加価値を有している。
*   実装への影響（第5回のスコープ）：LINEを使用することで、複雑な画面は簡略化し、APIエンドポイントへの直接的なリクエスト、または初期値のDB登録によって動作を確認する範囲を実装のゴールとする
*   リスクと対応（最低3件）：
    *   外部API（OpenWeatherMap）の仕様変更・停止： 気象データが取得できない場合に備え、APIレスポンスの型チェックを厳密に行い、異常時は「データ取得不可」の旨をLINEで通知するエラーハンドリングを実装する。また、将来的なプロバイダ変更（気象庁データの利用等）に対応できるよう、データ取得ロジックをモジュール化して疎結合に保つ。
    *   LINE IDおよびトークンの漏洩リスク： ユーザーの識別子であるLINE IDや、API利用に必要なチャネルアクセストークンをコード内にハードコーディングせず、必ず環境変数（.env）で管理する。また、データベースへの保存時は必要に応じて暗号化を検討し、APIレスポンスに機密情報を含めない設計を徹底する。
    *   通知スパム・不正利用の発生： 意図しない大量通知によるLINE APIの利用停止を防ぐため、1ユーザーあたりの1日の通知回数に制限（レート制限）を設け、判定ロジックに「最後に通知した時間」を記録するフラグを導入することで、過剰な通知送信を物理的に抑止する。
